# Implement

`implement <map-id>` delivers one approved Wayfinder ticket per invocation, then stops. This main session owns its claimed ticket from preparation through integration: research, behavior inventory, technical and UX design, implementation, tests, hands-on QA, evidence, landing and cleanup. Independent reviews use subagents. Other implementation sessions can each deliver one ticket against the same map; there is no coordinator or implementation delegation.

Read [map rules](map-rules.md) before the first map write. Wayfinder remains the durable record of requirements, dependencies, claims, decisions and evidence. Deliver approved acceptance and legacy parity except for explicit owner-approved divergences. Never redefine success to close a ticket.

## Start and resume

1. Check `wayfinder run assignment` for a runner assignment to this Codex thread. If present, use its `mapId` and target below; the prompt may contain only `$implement`. Then start with `wayfinder session start --isolated`. Save the returned ID in your session context and supply it as `--session <id>` on every map command, including reviewer assignments. Alternatively use `WAYFINDER_SESSION` in every map-command environment; do not assume shell exports survive tool calls. Resume with the same ID. Isolated start never changes the repository's legacy ambient session; do not use ambient identity or `session start --new` for concurrent implementation.
2. Open the assigned or named map (or the sole active map), its specification, active milestone, working knowledge and owner questions. Read repository instructions and the effort brief. If several maps are possible without a runner assignment, ask which one.
3. In execution, claim an assigned ticket with `wayfinder claim <map>/<ticket> --session <id>` or an assigned slot with `wayfinder claim <map> --milestone <key> --session <id>`. If the assignment is no longer claimable, run `wayfinder claim <map> --next --session <id>` and follow that result. Without an assignment, run `claim --next` directly. It atomically resumes your claim, takes ready M0 work first, then a ready AFK ticket in the active milestone. When that milestone has no open execution tickets, it claims the milestone slot instead. A slot receipt has `claim.milestoneKey`; a ticket receipt has `claim.ticketId`. `claim: null` means another session owns the slot or there is no available work. If you receive the slot, compare the milestone's full scope with delivered evidence, then create one planning or closeout ticket as described below. After a ticket claim, use the host's thread-title tool to name the current thread `<ticket-id> - <ticket title>` with its exact ID and title. If the host has no rename capability, continue the ticket.
4. Claim the ticket or milestone slot before researching or designing. Own at most one execution claim. For a ticket, read its full brief, designs, findings, subtasks, checkpoint and worktree record. Establish exact prerequisite source on integration, not a title, another branch or a passing test count.
5. For a preserved ticket, inspect its source, commits and evidence before changing anything. Another session's claim is not abandoned just because it is old. Take over only after its owner has stopped/released it or the human explicitly directs takeover; record the handoff and use `--force` only when needed for that established takeover. For a legacy session with several claims, checkpoint and release its extra claims before resuming one; never release another live session's work.

The invocation authorizes delivering only the selected ticket until complete, paused or blocked. Answer owner questions briefly and continue that ticket. Another ticket requires a new invocation or an explicit owner request to continue. When blocked, record the exact cause, preserved source, completed gates and next action; release your claim and stop. Record genuine dependencies and release together with `wayfinder dependencies <ticket> --release --expect <ticket revision>` and `{blockedBy:[...],reason}` so another session cannot claim between release and blocking. Include existing blockers in that replacement list. If a human decision blocks it, link an owner question and use an explicit HITL prerequisite where appropriate. Never steal a claim or weaken a gate to keep busy.

## Plan and activate

For `decision_ready`, plan and activate from a fresh session, not the session that completed decisions. Read the specification and approved decisions; synthesize a missing specification with `to-spec`. Inspect the code yourself. Propose the first coherent feature slice, complete ticket outcomes and dependencies, the milestone roadmap and the integration baseline directly to the owner in this session. The owner-question inbox is available only during execution. Activate only with their approval and the exact map revision. Concurrent activation attempts are revision-guarded; after a conflict, read the approved result instead of activating again.

A decision-phase map needs its unresolved decisions settled first, one `decide` invocation per ticket. A complete map needs a new owner request before substantial new work.

Planned milestones hold scope, not execution tickets. Record deferred obligations in the relevant milestone description with owner approval for a scope change; preserve detailed source references there for its future planner. An active milestone's slot is open only when it has no open execution tickets. The slot owner checks the full description and history, ignoring cancelled, ruled-out and superseded tickets as delivery evidence. With no resolved ordinary work, create a planning ticket unless a resolved planner already found no work to file; in that case seek an owner scope decision. After ordinary work ends, compare delivered evidence with every obligation: create a planning ticket for gaps or a closeout ticket when coverage appears complete. Add exactly one such ticket with `--expect <map revision>`, basis `discovery`, and `executionRole: planning` or `closeout`. The add operation transfers the slot claim to the new ticket atomically. On conflict, re-read the map and follow its current claim. Planning and closeout each count as one invocation; completing planning does not authorize claiming a delivery ticket. A planner files work tickets for remaining scope before resolving. Planning is main-agent work, and changing milestone scope still needs the owner. If the slot owner cannot proceed, release it with `wayfinder release <map> --milestone <key> --session <id>`.

## Ticket preparation

Create a fresh branch and worktree from current integration for each new ticket; resume a preserved ticket in its recorded worktree. Keep the integration checkout on its recorded branch. Record `wayfinder worktree <ticket> --path <path> --branch <branch> --base <starting SHA>`. Work only in your ticket checkout, including research, inventories, designs and implementation documents. Preserve uncommitted work and identify its owner; never silently omit, stash or delete it.

Use or create the repository's effort brief with map/specification, integration branch and checkout, test/build conventions, runtime setup and durable evidence location. Prepare a missing brief on the first owning ticket's branch; interim assignments can reference it there. Merge it with that ticket. Do not create a competing global progress ledger.

Default to focused tests, one independent code review when scope or risk warrants it, and main-agent QA of affected UI and journeys. Add requirements or design review for new or changed requirements or material unsettled design decisions.

Keep preparation in one concise linked record by default, combining inventory, field research, design decisions and verification mapping where they overlap. Use existing authoritative records; separate documents serve distinct consumers or substantial detail. Ticket fields summarize and link that record.

Before implementation:

- **Inventory:** author or update the legacy behavior inventory at the required granularity, naming sources, consumers, permissions, variants, recovery and persisted consequences. A requirements-reviewer subagent verifies new inventories, newly researched behavior and changed interpretations before the affected implementation. Reuse verified rows and their clearance while sources and assumptions hold; a correction implementing an already verified rule proceeds with applicable code review and focused checks. Return inventory corrections to the same verifier.
- **Technical design:** record owners to reuse, public contracts, schema/migration changes and named consumers for shared contracts, APIs, data models, packages or shared owners. Research and author this yourself. Record design changes and their acceptance consequences; product or divergence decisions remain the owner's.
- **UX design:** for a new/reorganized screen or substantial flow, author the design from verified requirements and repository design contracts before building. Use a design-reviewer for any required independent design review. Small UI changes need no separate design stage.
- **Readiness:** trace requirements to consuming surfaces and meaningful witnesses, including required person-operable states and how to reach them. Verify prerequisites are integrated. Keep brief, designs and subtasks in their owning fields and link substantial detail once.

When introducing or materially changing a shared transaction, concurrency, retry or preview/confirm protocol, trace the affected production path in the existing technical design: mutable inputs and competing writers, protection and lock order, resource budgets, and replay, no-op and rollback behavior where applicable. Name the focused witnesses for those interactions. Preparation is ready when the trace accounts for the affected participants in production composition and its early engineering review is clear. Consumers using an established protocol can cite its verified design and describe only their differences; keep analysis within the changed behavior.

Size tickets by complete screens or comparably substantial capabilities. Separate only substantial shared subsystems with named consumers. Keep ordinary sections, controls, fixes and review rounds on the owning ticket. Derive the checklist from the outcome: domain/API/persistence, migrations, permissions, consumers, structural acceptance and verification. Check off only delivered and verified work; add discovered work within scope, undo invalidated items.

## Implementation and QA

Implement the ticket yourself, including tests, migrations, generated output and supporting documents. Fix a prerequisite inside your ticket when it belongs to its scope. For another ticket's missing prerequisite, record the dependency and checkpoint; never copy an unfinished supplier branch or edit generated output by hand. A small repair uses accepted integration contracts and does not wait for unrelated supplier work. Substantial shared work discovered during a ticket follows the sizing rules, not ad hoc partial-release choreography.

When verification needs a runtime or databases, use the repository's ticket-environment launcher when available. Bind its environment to the claimed ticket, worktree and explicit session identity; keep that reference in the checkpoint. Run authentication, generation and verification through its scoped command wrapper, and database-heavy checks through its capacity-limited executor. Keep runtimes, ports, generated output and test data isolated per worktree using repository mechanisms. Worktrees alone do not isolate external databases or shared generation directories. Use the repository's resource lock/fixture executor where isolation is unavailable; hold it only for the operation that needs it. Never stop another session's processes or overwrite its output. Identify candidate, origin, process, API health and cleanup ownership once; refresh after a runtime change or failure.

Perform [Hands-on QA](implement-qa.md) as you complete the changed UI and delivered or endangered journeys, then freeze a committed candidate for independent review. You own QA. Retain its evidence when the reviewed candidate has the same tested source and qualified inputs. Review-driven corrections return to the same reviewer and receive affected QA. A final pass reconciles the candidate and evidence; additional execution addresses only a changed input or coverage gap.

Apply the installed humanizer skill whenever adding or changing human-facing text in the product UI, including labels, help, validation and error messages, within repository copy conventions.

## Independent reviews

Batch implementation review around a complete form, workflow or substantial shared contract with named consumers. Include its routine helpers and wiring in that review. Request earlier supporting-source review when its clearance unblocks dependent implementation or resolves a concrete risk before proceeding; state that reason in the assignment. Keep the required pre-implementation inventory, UX and protocol-design gates at their prescribed points.

For the protocol changes identified in technical preparation, assign the ticket's code reviewer an early review of the design against existing source and production composition before the affected implementation. Resolve concrete omissions in that scope, then retain the same reviewer for code review. Design clearance covers the proposed interactions; implementation still needs its applicable review and checks.

Every required review is a subagent assignment. Main-agent inspection is preparation and self-checking, not independent clearance. Preserve proportional oversight: small low-risk work needs focused checks; substantial changes and meaningful correctness risks need independent code review, including small security, authorization, data-integrity, migration, destructive-operation or shared-contract changes. Required inventory verification and milestone completion review remain independent even though you authored the inventory or performed QA.

Use installed `wayfinder-code-reviewer`, `wayfinder-requirements-reviewer` and `wayfinder-design-reviewer` roles for applicable reviews. Assign distinct questions: the requirements reviewer verifies inventory authority and completeness before code; one code reviewer checks implementation against those verified requirements and engineering rules; a design reviewer checks material UX decisions when an independent design gate applies. Main-agent QA establishes rendered usability and working journeys. Use existing contracts and verified designs for routine changes. At milestone closeout, requirements review checks combined acceptance and integration gaps using qualified ticket evidence. In a host without native role selection, load the installed role instructions into a read-only reviewer assignment. Preserve the configured model; role definitions use high reasoning effort. A missing required review capability is a blocker.

- Start one reviewer per ticket and review role. Reuse that same subagent for fixes, re-review and integration refresh. Do not create a fresh reviewer for each round or use a reviewer who helped author the candidate.
- Record reviewer host, agent ID, role, reviewed candidate, findings and evidence in a durable ticket handoff referenced by its checkpoint. On resume, try the same agent if the host can continue it. If it is unavailable, record that fact and a replacement; supply the prior findings/evidence and require independent inspection. Never imply an unavailable agent was resumed.
- Assign by reference: ticket, explicit session ID, effort brief, candidate/base, requirements/design/inventory and exact relevant test files. Follow-ups name the previously cleared candidate and scope, changed inputs, affected evidence and the next action. Reviewers read source independently, record findings, and close their own findings only after verification. They do not edit candidate source or Git state.
- Batch corrections for a review round. Keep reviewers available until the ticket lands. Wait for their result; do not poll unchanged state or repeatedly reconstruct their work. Return receipts in at most ten lines: verdict, candidate/scope, findings, retained/refreshed evidence and blockers. Details remain in durable records.

At completion, include the owning guide, public entry and focused test path in
the durable receipt for a new or moved shared owner. State which consumers
migrated and why any similar implementation remains separate. Keep the user
receipt concise; link this record instead of repeating its inventory.

## Evidence and resumption

Keep one durable evidence record per ticket, referenced by checkpoints and resolution. Preserve reviewer identities, exact candidates and qualified inputs, commands, selected cases, verdicts, necessary readbacks and relevant failure/correction evidence outside disposable worktrees. Counts alone are not evidence; inspect actual assertions and consumer behavior. Missing historical evidence is unknown; reconstruct agent-owned evidence internally rather than asking the owner to supply missing agent logs.

Before repeating a check or review, compare the candidate and relevant inputs with its receipt. Record what remains applicable and what is invalidated or missing, with the specific change or gap that requires new evidence. Include affected contracts, consumers, dependencies, generation/migration inputs, fixtures and runtime configuration. Reuse unaffected clearance and run only the checks that address that change or gap. A new commit, checkpoint or reviewer handoff alone does not invalidate evidence; a changed requirement can invalidate it even when executable source is unchanged.

Each checkpoint names the phase, exact candidate, cleared scope, invalidated or missing evidence (or none), next action and remaining blockers; link the durable record for reviewer identities, comparison basis and detailed receipts. Resume at that action after confirming the recorded inputs still apply. Keep the checkpoint within its map limit rather than copying the evidence record. `wayfinder validate` is payload-only and takes no session flag; inspect the actual write result too.

## Land and stop

1. Finish the whole ticket's acceptance, checklist and applicable reviews/QA. Supporting-source approval clears only its named scope; it does not close a screen ticket. Preserve unmerged work if completion is blocked.
2. Refresh the ticket branch against current integration. Record the full integration SHA as the qualified base. Compare public contracts, affected consumers, generation/migration inputs, dependencies and composition wiring even after a clean textual merge/rebase. Resolve conflicts in the ticket worktree. Return invalidated review to the same reviewer and refresh affected QA; retain unaffected evidence with its comparison basis.
3. Commit the final candidate, confirm clean worktrees, and use `wayfinder land <ticket> --candidate <full SHA> --base <qualified integration SHA> --session <id> --input <resolution.json>`. The payload has `resolution`, `decisionSummary` and optional evidence artifacts; omit a commit artifact because `land` supplies it. Wayfinder serializes landing across the repository, refuses stale integration or a moved candidate, fast-forwards integration and resolves the ticket. It does not rebase, run reviews/tests, push, or clean up for you.
4. If integration advanced first, refresh and qualify outside the landing lock, then retry. If Git merged but the map write failed, preserve everything and retry the same candidate; ancestry permits completion of the ticket record without another merge. Do not force/reset integration. All implementation sessions must use `land`; direct commits/merges to the integration checkout bypass its protocol.
5. Verify the resolution and reachable commit, retain durable evidence, stop and remove your ticket environment after retaining required evidence, delete disposable credentials/output, and remove/archive the merged ticket worktree using the host's appropriate tool. Release reviewer resources after landing. Report the completed ticket, landed commit, and only items that need the owner's attention; write it so it can be read in ten seconds: lead with the result, one fact per line, nothing the owner can't act on. Then stop. Leave the next ticket unclaimed.

Plain-directory work has no Git landing: freeze the candidate scope, retain files-and-checks evidence and use `resolve`. Do not run concurrent sessions against the same mutable files in that mode. Push, publication and destructive cleanup need their separate authorization.

## Milestone closeout

When `claim --next` returns the empty milestone slot after ordinary work, compare every obligation in the description against delivered evidence. Create one planning ticket for uncovered scope. Only when coverage appears complete, create one `executionRole: closeout` ticket through the slot with subtasks for combined journeys, independent completion review and evidence. A session with no claim stops with an accurate queue state. Completing the last ordinary ticket does not authorize starting closeout in the same invocation.

The closeout owner qualifies existing evidence for the milestone's main journeys on integration and exercises uncovered cross-ticket behavior or invalidated paths. Send a requirements-reviewer, who neither implemented the work nor authored its inventories, every milestone criterion, approved exception and delivered evidence. Keep the completion report in durable verification storage; the owner may commit it on the closeout branch. Gaps become work tickets in the milestone. Record those tickets as closeout dependencies and release it atomically with `dependencies --release --expect <revision>`, then stop. A later invocation can resume closeout with the same reviewer when they land. Refresh any invalidated evidence if integration changes.

Once clear, land/resolve the closeout ticket; its claim returns to the milestone slot if no work remains open. Run `wayfinder milestone complete` from that same session with the independent review payload and current map revision. Before completing, confirm there are no newly opened gaps and the reviewed integration inputs still apply. A concurrent completion is resolved by reading the recorded result; never repeat or overwrite it blindly. No additional owner approval is needed for a clean, in-scope completion. The next milestone activates automatically; leave its tickets unclaimed. Finish the map only when scope, fog, milestone gates and reachable delivery evidence support completion. Complete the closeout's cleanup and report, then stop.

## Owner decisions, pause and wind-down

Ask unresolved product/acceptance questions and proposed owner-basis scope changes through `wayfinder question ask`, one decision per question. Reference affected tickets. Check existing questions before adding another. A reviewer returns questions to you; every implementation session can contact the owner through the map. Hold only affected work. Record answers in their owning contracts and close the question with the owner's words. Do not use questions for status reports or missing agent-owned receipts.

Lead owner messages with what needs deciding or what now works; give concrete ticket/milestone context and concise options. Avoid speculative time estimates and repeated unchanged status.

### Ticket worktree lifecycle

Keep the ticket branch and worktree while the ticket is open, including pauses,
blocked work and wind-downs. Leave tracked and untracked source in the checkout,
preserve an independent backup and record the resume point. Stop unused owned
processes and remove disposable credentials or scratch output. Remove or archive
the ticket worktree only after the ticket is complete and its candidate has
merged into integration, following [Land and stop](#land-and-stop).

A **pause/stop** stops your work and interrupts your running reviewers. Preserve source and evidence, checkpoint the candidate, completed gates, reviewer identities, blocker and next action; release your claim once no worker is changing it. Report what stopped and anything you could not stop. Resume only on the owner's instruction.

A **wind-down** starts no new tickets or review assignments. Finish only the currently authorized bounded work, preserve its candidate and next gate, then release your claim and unused resources. Do not infer whole-ticket acceptance from a partial delivery. Scope a pause or wind-down to your session unless the owner explicitly addresses the whole effort; do not interfere with other implementation sessions.
