# Linux metric sources for the resource monitor

Decision research for `wf-48ebf7/t-1aa5ed` (2026-10-05). This report identifies available interfaces and proposes collection rules; it does not choose product behavior beyond the confirmed one-screen scope.

## Verified interfaces

| Reading | Primary interface and semantics | Important limit |
| --- | --- | --- |
| CPU aggregate/per-core usage | `/proc/stat` has an aggregate `cpu` row and `cpuN` rows of cumulative time in USER_HZ. Derive usage from two samples. [Kernel procfs](https://docs.kernel.org/filesystems/proc.html) | First sample has no rate; `iowait` is not literally processor work and can be unreliable. |
| RAM and swap | `/proc/meminfo`: `MemTotal`, `MemAvailable`, `SwapTotal`, `SwapFree`; `MemAvailable` estimates memory available for new work without swapping. [Kernel procfs](https://docs.kernel.org/filesystems/proc.html) | Do not equate `MemFree` with useful free RAM or add overlapping cache fields. |
| CPU temperature | `/sys/class/hwmon/hwmon*/temp*_input`, with `name` and optional `temp*_label`; inputs are normally millidegrees Celsius. [Kernel hwmon ABI](https://docs.kernel.org/hwmon/sysfs-interface.html) | Labels and channels vary. An arbitrary motherboard or GPU sensor must not be called CPU temperature. |
| Network traffic | Per-interface RX/TX byte counters through rtnetlink `RTM_GETLINK`/`RTM_GETSTATS` and `rtnl_link_stats64`; `/proc/net/dev` is a simpler historical alternative. [Kernel network statistics](https://docs.kernel.org/networking/statistics.html) | Counter deltas are rates; interfaces can reset or disappear. Summing a VPN and its physical carrier counts the same traffic twice. |
| Disk I/O | `/proc/diskstats` or `/sys/block/<device>/stat` cumulative read/write sectors. [Kernel I/O statistics](https://docs.kernel.org/admin-guide/iostats.html) | Partition and whole-device figures overlap; device-mapper and physical layers may also overlap. Capacity is a separate metric. |
| Free storage | `statvfs(path)`: `f_blocks`, `f_frsize`, and `f_bavail` give total bytes and space available to an unprivileged user. [Linux man-pages](https://man7.org/linux/man-pages/man3/statvfs.3.html) | `f_bavail` can differ from `f_bfree`; it is the useful number for “GB left.” |
| Mount identity | `/proc/self/mountinfo` records mount point, root within filesystem, filesystem type, source, and `major:minor` (`st_dev`). [Kernel procfs mountinfo](https://docs.kernel.org/filesystems/proc.html) | Bind mounts and Btrfs subvolumes can give distinct mount entries over shared capacity. |
| NVIDIA GPU | NVML enumerates devices and exposes utilization, framebuffer memory used/total, and temperature. [NVIDIA NVML guide](https://docs.nvidia.com/deploy/nvml-api/latest/index.html) | API calls can return unsupported, missing-device, or other errors; GPU memory utilization is bandwidth activity, not VRAM occupancy. [NVML device queries](https://docs.nvidia.com/deploy/nvml-api/latest/api/group__nvmlDeviceQueries.html) |
| AMD GPU | The `amdgpu` DRM device exposes `gpu_busy_percent`, `mem_info_vram_total`, and `mem_info_vram_used`; associated hwmon exposes temperature channels. [Kernel amdgpu monitoring](https://docs.kernel.org/gpu/amdgpu/thermal.html), [VRAM ABI](https://docs.kernel.org/gpu/amdgpu.html) | Attributes depend on GPU/driver. `mem_busy_percent` is VRAM activity, not bytes allocated. [Kernel amdgpu monitoring](https://docs.kernel.org/gpu/amdgpu/thermal.html) |
| Intel GPU | Level Zero Sysman defines engine-activity counters, memory module state/properties, and temperature sensors. [Engine API](https://oneapi-src.github.io/level-zero-spec/level-zero/latest/sysman/api/apis/engine.html), [memory API](https://oneapi-src.github.io/level-zero-spec/level-zero/latest/sysman/api/apis/memory.html), [temperature API](https://oneapi-src.github.io/level-zero-spec/level-zero/latest/sysman/api/apis/temperature.html) | Runtime/driver support varies and APIs explicitly report unsupported, unavailable, and insufficient permissions. Intel `i915`/`xe` also export optional DRM client `fdinfo`, but it is per-client accounting, not a straightforward whole-device total. [Kernel DRM usage stats](https://docs.kernel.org/gpu/drm-usage-stats.html) |

## Proposed collection rules

1. Discover CPU rows, hwmon devices, network links, block devices, mounts, and DRM/NVML/Sysman GPUs at runtime. Key GPU identity by PCI address when available and keep independent fields per device. Treat absent or failing fields as **unavailable**, never zero. Refresh discovery when devices appear/disappear; do not assume `card0`, a fixed interface name, or a fixed hwmon number. The amdgpu files belong to the DRM device, while hwmon labels identify temperature channels. [Kernel amdgpu monitoring](https://docs.kernel.org/gpu/amdgpu/thermal.html), [hwmon ABI](https://docs.kernel.org/hwmon/sysfs-interface.html)
2. For NVIDIA, use NVML directly through a Rust binding such as [`nvml-wrapper`](https://github.com/rust-nvml/nvml-wrapper); its own API exposes memory, utilization, and temperature. For AMD, read documented sysfs values. For Intel, prefer a runtime-loaded Sysman provider where available and classify memory by `ZES_MEM_LOC_DEVICE` versus `ZES_MEM_LOC_SYSTEM`: only device-local capacity should be labeled **VRAM**. An integrated GPU using system memory should say **shared GPU memory** or **VRAM unavailable**, without inventing a dedicated capacity. [Sysman memory API](https://oneapi-src.github.io/level-zero-spec/level-zero/latest/sysman/api/apis/memory.html)
3. Calculate Intel engine busy from activity-counter deltas over elapsed time, selecting a documented aggregate engine group if offered; otherwise label the shown engine/group instead of claiming it is an exact device-wide percentage. Do not add independently busy engines into a purported GPU percentage. Consider `i915` PMU/fdinfo support as a fallback investigation during implementation, with permission failure presented as unavailable. DRM `fdinfo` expressly varies by driver and warns against double counting clients. [Sysman engine API](https://oneapi-src.github.io/level-zero-spec/level-zero/latest/sysman/api/apis/engine.html), [Kernel DRM usage stats](https://docs.kernel.org/gpu/drm-usage-stats.html)
4. Choose a CPU package/die channel by driver and label where identifiable. Preserve the source label for ambiguous channels and show CPU temperature unavailable if attribution cannot be established. Associate AMD GPU hwmon through its device path. Missing sensors must not disable other metrics. [Kernel hwmon ABI](https://docs.kernel.org/hwmon/sysfs-interface.html)
5. Show `/` and `/home` capacity, comparing their filesystem device identity (`st_dev`/mountinfo `major:minor`) before producing two capacity gauges. If they share capacity, show one gauge with both path labels; if distinct, show both. Use `statvfs` separately on the paths and do not sum their totals. Extra mounts remain discoverable on demand. [Kernel mountinfo](https://docs.kernel.org/filesystems/proc.html), [Linux statvfs](https://man7.org/linux/man-pages/man3/statvfs.3.html)
6. For network, prefer a selected active link and expose other links on demand; do not silently add overlapping physical, bridge, and VPN links. For I/O, retain per-device identity and select a single block layer for any displayed aggregate; never sum a partition with its parent or a mapped device with its backing device. [Kernel network statistics](https://docs.kernel.org/networking/statistics.html), [Kernel I/O statistics](https://docs.kernel.org/admin-guide/iostats.html)
7. Use monotonic elapsed time for byte/sector deltas. Warm up a newly discovered counter; a decrement, missing counter, zero/invalid interval, or restart produces a gap and new baseline, not a negative spike. Use checked arithmetic and bound the time-series buffer. These are proposed reliability rules derived from the cumulative-counter interfaces above. [`sysinfo` refresh APIs](https://docs.rs/sysinfo/latest/sysinfo/) are a possible Rust convenience layer for CPU/memory/network, while [`rustix::fs::statvfs`](https://docs.rs/rustix/latest/rustix/fs/fn.statvfs.html) covers capacity. Confirm each abstraction's units, refresh timing, and device identity before choosing it.

## Verification route

- **Here, live NVIDIA:** `lspci` identifies an NVIDIA AD102 GeForce RTX 4090 at PCI `0000:01:00.0`. On 2026-10-05, `nvidia-smi --query-gpu=index,uuid,pci.bus_id,utilization.gpu,memory.used,memory.total,temperature.gpu --format=csv,noheader` returned `0, GPU-80228cd7-c33f-d72a-7c07-f742f7e1ca92, 00000000:01:00.0, 9 %, 1852 MiB, 24564 MiB, 45`. This proves the host can provide the four requested NVIDIA readings at that instant; implementation should compare its provider with NVML/`nvidia-smi` under idle and GPU load, plus driver loss/unavailable simulation. `nvidia-smi` is built on NVML. [NVIDIA NVML guide](https://docs.nvidia.com/deploy/nvml-api/latest/index.html)
- **Here, storage:** `findmnt -T /` and `findmnt -T /home` report Btrfs subvolumes `[/root]` and `[/home]` on `/dev/nvme0n1p3`, both `0:35`; a correct overview presents shared capacity once. [Kernel mountinfo](https://docs.kernel.org/filesystems/proc.html)
- **AMD/Intel without hardware:** feed parsers/provider adapters fixed `amdgpu` sysfs/hwmon and Level Zero response fixtures covering complete values, absent files/functions, permission errors, multiple GPUs, zero/unknown capacity, device removal, and counter reset. Validate units, device matching, and unavailable UI states. Fixtures establish software behavior, not live vendor compatibility; record AMD/Intel paths as hardware-unverified at release as the owner allowed.
- **Host-independent fixtures:** `/proc/stat`, `/proc/meminfo`, network and disk counter pairs, mountinfo plus `statvfs` results for same/different filesystems; include changing CPU count, link rename, layered block devices, and Btrfs subvolumes. Verify first-sample gaps, no double counting, and bounded history.

## Open implementation questions

- Which Intel runtimes/devices on target distributions provide all Sysman fields without elevated permissions, and whether a documented i915/xe fallback is needed for full coverage, require hardware and packaging validation. Do not state universal live Intel support from the API specification alone.
- CPU package temperature identification across heterogeneous motherboard sensors needs fixture examples and live hardware checks. Exposing a source-labelled reading is safer than silently choosing an arbitrary `temp1`.
