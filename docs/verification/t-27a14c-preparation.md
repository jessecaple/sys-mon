## Technical design and named consumers

Create `src/lib.rs` with a public `telemetry` module; keep Linux parsing, hwmon selection and worker ownership in private children of that module. The small public model is `Snapshot` with typed CPU, memory, swap, GPU, network and primary-storage fields; each measurement is `Reading<T>` (`Value` or `Unavailable`) and exposes its unit and any capacity/threshold separately. An unavailable field never borrows the previous displayed value. RAM/swap capacities can be zero or unknown without creating a percent. Temperature is degrees Celsius with an optional reported max threshold. GPU, network and storage start unavailable until their owning tickets implement providers; the model is their named contract, not simulated data.

`Sampler` is the synchronous test seam: injected `Probe` reads host text and enumerates hwmon channels; injected monotonic `Duration` drives one `tick` returning a complete snapshot. The production `LinuxProbe` reads procfs/sysfs. A CPU baseline belongs to the sampler, not to global state. Individual source reads are independent so memory failure does not erase CPU or temperature. The session owns one host worker and a latest-snapshot slot (`Arc<Mutex<Snapshot>>`); the GTK client clones the current snapshot, so there is no unbounded event queue. It starts one worker, samples immediately, then uses interruptible timed waiting after work. It does not schedule another tick while one is in flight. `stop` signals cancellation and joins the worker; `Drop` also stops. The host worker only performs procfs/sysfs reads. The GPU ticket must isolate potentially unbounded vendor calls in killable owned helper processes and merge provider fields atomically into the same latest snapshot; no later ticket may pass such a call into the cooperative host worker. Provider writers use short slot locks only to replace fields, never while reading hardware or awaiting helpers. Snapshot reads also use short locks; no GTK code executes under the slot lock. There are no network/database resources or migrations.

Competing writers are the host worker, future GPU helper reader and future network/storage worker. They own disjoint snapshot fields and replace those fields under one short lock; stop is signaled before joining/terminating workers. Lock order is cancellation signal, then no lock while joining; the snapshot lock is never held across I/O or process wait. A stopped session rejects later updates by generation/cancellation check. Slow host reads delay only that host worker, with no queued catch-up. Slow optional provider calls require the GPU helper boundary above. Memory budget is one latest snapshot, one CPU baseline and current hwmon enumeration; no history. Repeated calls to `stop` are no-ops. Failure publishes unavailable fields on that tick and valid recovery publishes values on a later tick. If a worker panics, its fields must become unavailable rather than silently remaining stale; implement an explicit panic guard or catch/unwind boundary.

The dashboard ticket consumes `TelemetrySession::snapshot()` on GTK's main loop and calls `stop` when its only window closes. The GPU ticket owns vendor provider and helper implementation. The network/storage ticket owns rate baselines, current device identities and filesystem identity; it uses this snapshot model, not the CPU baseline. Public contract changes that affect those consumers must be compared on integration refresh.

## Readiness and verification map

- Source fixtures exercise public `Sampler::tick` results for CPU warm-up/reset and units; parsing-only tests are secondary.
- Controlled probe errors and hwmon sets exercise independently unavailable fields, attributed sensor choice, no threshold, removal and recovery.
- A deterministic source with a blocked/slow tick exercises one in-flight host read, no queued catch-up and stop during sleep and in-flight work. A live session process check confirms no host worker remains after stop.
- On the available host, compare `Snapshot` RAM/swap values to `/proc/meminfo` semantics, CPU usage to consecutive `/proc/stat` samples, and CPU temperature to the attributed `coretemp` channel. These are plausibility checks, not vendor coverage.
